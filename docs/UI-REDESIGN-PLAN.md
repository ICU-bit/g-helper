# UI 重构计划

## 目标

将主界面从当前的长页面调整为更聚焦的入口：一级页面默认只显示性能模式和显卡模式；屏幕、灯效、电池、外设、矩阵、风扇、更新和其他高级功能进入二级设置或现有独立窗口。

## 实施策略

1. **第一阶段：视图折叠，不迁移底层逻辑**
   - 保留 `SettingsForm` 作为硬件状态和 UI 更新的 façade。
   - 增加首页/更多设置视图切换，默认展开性能模式和显卡模式。
   - 其他现有面板通过统一的折叠状态隐藏或展开，避免复制按钮事件和硬件控制逻辑。
   - 保留电池、退出、版本和必要的状态入口，避免隐藏后无法操作或退出。

2. **第二阶段：复用现有二级窗体**
   - 风扇与功耗：复用 `Fans`。
   - 键位、服务和高级选项：复用 `Extra`。
   - 掌机控制：复用 `Handheld`。
   - Matrix/Slash：复用现有 `Matrix` 和 `Slash`。
   - BIOS/驱动查询：复用 `Updates`。
   - 键盘和鼠标：继续复用动态创建的独立设置窗体。
   - 保留托盘菜单和命令行入口作为兼容入口。

3. **第三阶段：按功能组迁移剩余嵌入面板**
   - 在前两阶段稳定后，再考虑把显示/灯效、设备/电池等功能组抽成独立二级窗体。
   - 每次只迁移一个功能组，通过 `SettingsForm` 的 façade 保持已有硬件回调和生命周期稳定。

## 约束与维护原则

- 不复制 GPU、性能模式、电池、屏幕和外设的状态机；继续复用现有事件处理器和控制器。
- 不在第一阶段大规模重排 `Settings.cs` 或 `Settings.Designer.cs`，减少与官方 `upstream` 同步时的冲突。
- 任何动态硬件刷新都必须同时考虑“设备是否支持”和“用户当前是否折叠”两个状态，不能无条件重新显示面板。
- 新增页面必须接入现有主题同步、窗体所有权、关闭清理、焦点判断和高 DPI/多语言布局。
- 每个阶段单独构建验证，并保持小范围提交。

## 风险

- 当前多个硬件模块直接依赖 `Program.settingsForm` 的控件；直接搬迁所有控件会造成较大范围的生命周期和回调改动。
- 主窗体尺寸变化会影响现有二级窗体的定位逻辑，尤其是 `Fans`、`Updates`、`Matrix` 和 `Handheld`。
- Designer 文件改动较容易与官方更新冲突，因此只在对应布局变更时修改。
